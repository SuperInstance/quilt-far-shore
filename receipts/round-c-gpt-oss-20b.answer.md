### Flow Calculus  
- **BREAK** – The core of Flow Calculus is a *pure reduction* over an append‑only ledger. In practice this means iterating over every entry on each `diff`, `integrate`, or `lag` call. With a JSONL ledger stored in Cloudflare Workers or a Node process, that’s O(N) work per operation, blowing past the 10 000 request/minute limit and exhausting the 1 GB RAM quota. The naive discrete differencing also turns any small write‑noise or out‑of‑order entry into a high‑frequency oscillation in the derivative cell, which immediately triggers false interventions. Late‑arriving entries corrupt the integral because the integral is not re‑computed for past windows, so the “accumulated urgency” is stale.  
- **SNAKE OIL** – The claim that “operators gain warmth velocity and accumulated urgency as first‑class objects” is just a fancy way of saying “add a column to the ledger that holds a derivative or integral.” That’s nothing new – it’s exactly what a spreadsheet or a time‑series database does. The novelty is just a rebrand of linear algebra over time.  
- **FALSIFIER** – Feed a constant stream of values (e.g., the number 42) and compute `diff` over it. If the derivative cell shows any non‑zero variance larger than 1e‑6, the implementation is already noisy. Conversely, feed a synthetic stream with a known sinusoidal component and measure the error between the computed integral and the analytic integral; an error >1 % proves the reduction is incorrect.  
- **VERDICT** – **KILL**. The fundamental mismatch between pure reductions and the constraints of cheap, append‑only ledgers makes the primitive unusable without a wholesale redesign (e.g., incremental smoothing or a streaming analytics engine).  

### Invariant Monitor  
- **BREAK** – The monitor is defined as a *pure function* over a projection that is evaluated on *every* flow entry. In a real system that writes thousands of entries per second, re‑evaluating every invariant on each write is O(M·N) (M invariants, N entries) and will saturate the CPU and memory of a Cloudflare Worker. The “sealed anomaly cell” never gets garbage‑collected, so the ledger grows linearly with the number of violations, eventually exceeding storage limits. Moreover, invariants that depend on moving aggregates (e.g., a 5‑minute moving average) freeze the target: the invariant will never be true once the moving window starts, causing a flood of false positives that operators must mute.  
- **SNAKE OIL** – “Continuous assertions as objects” is simply a rebranding of runtime assertions or alert rules that are already common in monitoring stacks (Prometheus alerting, Grafana). The claim that this is a new paradigm is unfalsifiable; any system that can evaluate a function over a stream has already achieved this.  
- **FALSIFIER** – Create a ledger that writes a constant value every millisecond and define an invariant `value < 10`. Because of floating‑point rounding noise, the invariant will toggle between true and false. Count the number of false positives per second; if it exceeds 1 % of the writes, the monitor is too noisy to be useful.  
- **VERDICT** – **KILL**. The naive design is computationally prohibitive, produces unbounded anomaly logs, and is essentially a rebrand of existing alerting systems.  

### Evidence Key  
- **BREAK** – The primitive couples a *fact vector* (receipt presence, amount, date) with an *emotional vector* to form a compound key. This forces a fact extraction step at freeze time, which requires a model call or a regex parse. In a real ledger, that means re‑processing the entire receipt stream whenever a freeze occurs, defeating the goal of a lightweight, append‑only store. The regex‑based fact extractor overfits to one domain’s vocabulary, so it fails catastrophically on receipts from any other vendor. Moreover, the emotional vector is subjective and cannot be audited deterministically; two auditors may assign different tone vectors to the same event, breaking consistency.  
- **SNAKE OIL** – “Fact/emotion splitting” sounds novel but is simply a feature‑engineering trick that has existed in NLP pipelines for years. The claim that this unlocks executable freeze diagnostics is unfalsifiable; any system that can parse a document and attach a sentiment score can already do this.  
- **FALSIFIER** – Run the fact extractor on a held‑out set of receipts from a completely different domain (e.g., utility bills instead of retail receipts). Measure precision and recall of the extracted fact fields. A recall < 30 % proves the regex is domain‑specific. Alternatively, vary the emotional vector by two independent annotators and compute inter‑annotator agreement; an agreement < 0.4 indicates the emotional vector is not auditable.  
- **VERDICT** – **MUTATE** into a *structured, schema‑driven fact extraction* layer that uses a lightweight, deterministic parser (e.g., a hand‑crafted grammar or a small rule‑based engine) coupled with a fixed, auditable sentiment lexicon. Drop the “emotion‑only” part from the key and keep only the fact vector as the primary lookup key; store the tone vector as a separate, optional attribute that can be recomputed on demand. This retains the ability to audit facts while removing the costly, non‑reproducible extraction step.
